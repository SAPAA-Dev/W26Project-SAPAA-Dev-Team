# User Model Proposal (Sprint 2, Team Alpha)

Status: **approved** in PR #116 (Aaron and lamersc, 2026-09-30). Issue #75 applies the SQL.

This model is used by US 1.0.1 (profiles), US 1.0.2 (edit own profile) and US 3.0.2 (steward
designation). It also keeps a field for US 1.0.5 (activity points, Sprint 4).

## Current state on `main`

| Data | Where it is now | Problem |
|---|---|---|
| Login identity | `auth.users` | None. |
| Name, phone, avatar | `auth.users.user_metadata` | A user cannot read the `user_metadata` of another user without the service-role key, so US 1.0.1 cannot show other profiles from it. |
| Role, approval flag | `auth.users.app_metadata` | Only the server can write `app_metadata`, so a user cannot change their own role or approval flag (issue #5). |
| Legacy people | `luperson` | Mobile app writes `displayname` (`FNR/src/services/database.ts:312`). Google Sheets syncs the full table by `id` (`googleSheets/code.gs:368`). Web app only checks that an email exists (`webapp/utils/supabase/queries.ts:352`). The production columns are not in the repository. It has no link to `auth.users` (issue #38). |
| Inspections of a user | `form_responses.user_id` references `auth.users.id` | None. The inspection count can be calculated from this. |
| Steward of a site | Nothing | US 3.0.2 needs it. |
| Skills, focus areas | Nothing | US 1.0.1 and 1.0.2 need them. |

## Options considered

| Option | Summary | Result |
|---|---|---|
| A | New `profiles` table, keyed by the login id. `luperson` not changed. | Rejected. A person cannot exist without a login, so the legacy people in `luperson` can never move into it. The system keeps two people tables. |
| B | Add a login link and profile columns to `luperson`. | Rejected for now. The mobile app and the Sheets sync write to `luperson`, the production columns are not known, and the Sheets sync writes full rows. The risk is high and the change touches clients that Alpha does not own this sprint. |
| C | Keep profile data in `user_metadata`. | Rejected. Other users cannot read it without the service-role key (fails 1.0.1 AT1), and the user can change it without a server check. |
| **D** | **New `people` table with its own id. The login link is an optional column.** | **Proposed.** |

## Proposed model

`people` holds one row for each person with a login. `site_stewards` links one steward to each
site. `auth_user_id` is nullable, so a person without a login can be added later without a
schema change.

Contact details are not copied into `people`. Email and phone stay in `auth.users`, so there is
one copy of each (review of PR #116). Other users cannot read `auth.users` through RLS, so the
profile page (#76) reads them in a server action. Issue #76 decides which contact fields other
users see.

`luperson` is not linked. In the review of PR #116, lamersc asked to drop it from this model,
because the mobile app has not changed in two years. The web app only uses `luperson` to check if
an email belongs to a steward. If issue #38 imports legacy people later, it adds a link column then.

## Proposed SQL

This SQL is for review. A human applies it in the Supabase dashboard
(see `.agents/rules/database.md`).

```sql
create table public.people (
  id bigint generated by default as identity primary key,
  auth_user_id uuid unique references auth.users (id) on delete set null,
  display_name text not null check (length(trim(display_name)) > 0 AND length(trim(display_name)) < 30),
  skills text[] not null default '{}',
  focus_areas text[] not null default '{}',
  activity_points integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- site_id is the primary key, so a site has one steward and a new assignment replaces the old one (3.0.2 AT2).
create table public.site_stewards (
  site_id bigint primary key references public."sites_pa" (id) on delete cascade,
  steward_id bigint not null references public.people (id) on delete cascade,
  assigned_by uuid references auth.users (id) on delete set null,
  assigned_at timestamptz not null default now()
);

create index site_stewards_steward_id_idx on public.site_stewards (steward_id);

alter table public.people enable row level security;
alter table public.site_stewards enable row level security;

create policy "people are visible to signed-in users"
  on public.people for select to authenticated using (true);

create policy "users update only their own person record"
  on public.people for update to authenticated
  using (auth_user_id = auth.uid()) with check (auth_user_id = auth.uid());

-- RLS limits which rows a user can change. These grants limit the columns: a user can edit
-- only their profile fields, not activity_points (1.0.5), id, auth_user_id or the timestamps.
-- The profile edit endpoint uses the signed-in client, so these two rules are what stop a write.

create policy "site stewards are visible to signed-in users"
  on public.site_stewards for select to authenticated using (true);
-- No insert, update or delete policy: only admin server actions write site_stewards (see decision 3).

-- Make a person record when a user signs up.
create function public.create_person_for_new_user() returns trigger
  language plpgsql security definer set search_path = public as $$
begin
  -- left(..., 29) keeps long names inside the display_name check. If the check failed here,
  -- the sign-up itself would fail.
  insert into public.people (auth_user_id, display_name)
  values (
    new.id,
    left(coalesce(nullif(trim(new.raw_user_meta_data ->> 'full_name'), ''),
                  nullif(split_part(new.email, '@', 1), ''), 'New user'), 29)
  );
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.create_person_for_new_user();
```

The update policy limits a user to their own row. Column grants in the migration (#75) limit
them to `display_name`, `skills` and `focus_areas`, so a user cannot change `activity_points`,
`id`, `auth_user_id` or the timestamps. The migration also keeps `updated_at` current with a
trigger, and names the sign-up trigger `create_person_on_signup`.

The inspection count is calculated, not stored, so that it cannot become incorrect:

```sql
select count(*)
from public."form_responses" responses
join public.people person on person.auth_user_id = responses.user_id
where person.id = $1 and responses.is_active;
```

## Migration of current users

```sql
insert into public.people (auth_user_id, display_name)
select id,
       left(coalesce(nullif(trim(raw_user_meta_data ->> 'full_name'), ''),
                     nullif(split_part(email, '@', 1), ''), 'New user'), 29)
from auth.users
on conflict (auth_user_id) do nothing;
```

Done when `select count(*) from auth.users` equals
`select count(*) from public.people where auth_user_id is not null`.
No existing table is changed, so no data can be lost.

## Decisions

| # | Question | Decision | Source |
|---|---|---|---|
| 1 | Which model? | Option D: a `people` table with its own id. | Approved by Aaron and lamersc in PR #116. |
| 2 | Can other users see contact info? | Contact info is not in `people`, so `people` RLS does not expose it. Issue #76 chooses the fields that other users see. | Moved to #76. |
| 3 | Where is `role` stored? | In `app_metadata`, which only the server can write (issue #5). Only admin server actions write `site_stewards`, with the same admin check as Beta's admin route task. | Approved in PR #116, store decided by the move to `app_metadata`. |
| 4 | Separate profile email? | No. Email and phone come from `auth.users`. | lamersc's review of PR #116. |
| 5 | How many stewards per site? | One. A new assignment replaces the old one (`site_id` is the primary key). | US 3.0.2 AT2 (#62). If the client wants more, change the key to `(site_id, steward_id)`. |
| 6 | Table names? | No `W26_` prefix. | #73. |
| 7 | Can a profile use the current role? | It may display the role from `app_metadata`, but only as information; it must never authorize any action. | Fixed by the move to `app_metadata` (issue #5). |
